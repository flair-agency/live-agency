# ドメイン知識の実装案レビューと経緯

# 2026-09-13の知識配置方針

オーナーは、LIVEエージェンシー業をプラットフォームに共通する抽象ドメインとして`live-agency`に置き、その具象である各プラットフォームの知識を非公開リポジトリーに閉じ込めるよう指示した。Skillは抽象ドメインモデルとユースケースから導出されるため公開可能であり、Providerは含む知識により公開・非公開が分かれる。この指示を英語の[知識所有文書](../architecture/domain-knowledge-ownership.md)に反映する。配置方針は今回の明示指示で採用済みであり、本文のPR統合・既存知識の移管・公開設定の変更とは区別する。

2026-09-11の「両ドメインを親へ集約する」という方針を更新する。下記の旧説明と4つの実装案の図は当時の検討経緯として保存する。特に、公開予定の`live-agency`内にプラットフォーム固有ドメインを描いた旧パッケージ図は、今後の配置指示には使わない。本書全体の`pending`は残る実装案の状態であり、今回の明示指示を未決定とするものではない。

| 知識・成果物 | 配置と公開範囲 | 理由 |
| --- | --- | --- |
| LIVEエージェンシー業の抽象モデル・共通のユースケース | `live-agency`、公開可能な内容 | 共通業務を特定プラットフォームの制度や仕様から独立して説明する |
| プラットフォームの具象モデル・抽象との対応 | 非公開リポジトリー | NDA対象を含む知識を公開側へ伝播させず、同一プラットフォーム内の複数Providerが同じ意味を参照する |
| Skillの業務手順・判断・検証・引継ぎ | 抽象モデルとユースケースから導出する公開Skill | 特定画面の操作ではなく、業務目的と必要な中立の事実から手順を決める |
| Providerの取得・変換・サービス操作 | 含有知識により公開または非公開 | 公開可能な汎用操作と、保護される仕様の実装を区別する |
| 事業者固有の運用、実環境の対応設定 | 私有の運用文書・選択環境 | 一社の運用や実リソースを業界共通の不変条件にしない |

矢印は導出・対応・利用の関係を示し、npm依存や新APIの採用を意味しない。具象知識は非公開側で解釈し、公開Skillは正規化された事実を業務判断に用いる。公開Skillの説明は非公開仕様を読まずに理解できるものとし、実行に必要な私有知識・版・復旧手順は、権限のある人が選択済みProvider・環境の文書からたどれるようにする。秘密の内容やリンクを公開Skillへ埋め込んで引継ぎ経路を作らない。

## 今回の作業とAIポリシーレビュー

主分類E（知識の所有・情報境界）、副分類G（文書）。対象は親の方針文書と既存のレビュー・移行記録。Skill/Providerの実装、子pin、環境、運用ルール、配布を変更しない。最初の作業単位の完了条件は、今回の指示に沿った一貫した文書差分と確認可能なPRである。次の作業は私有の移管先と節単位の対応を具体化すること。復旧はこの文書差分のrevertであり、移管元の知識や既存実装は保持される。

`origin/main`の`e4b4351`から`codex/platform-knowledge-boundary`を作成した。元checkoutの`runtime`変更は保持し、独立worktreeで編集する。独立レビュー担当（gpt-6-astra / low）は現行の矛盾箇所の探索を読取専用で担当した。担当間で共有ファイルを編集しない。既存のIssue #2を継続し、PRは今回の配置方針のみを追跡する。

AIレビューの根拠は今回のオーナー明示指示、文書知識・言語・開発方針、全文を確認したPrivate Source Integration Guideである。旧方針による「両ドメインを親へ集約」「Providerは一律非公開」という記述を修正し、採用済み方針と未移管の内容、公開方針と実際の設定、公開Skillの理解と私有の実行手順へのアクセスを区別した。新たな業務不変条件や私有ソースの意味は追加していない。

変更文書11ファイルの相対リンク167件を確認し、欠落0件。未展開コンポーネントの参照先8種類は親が指定する子commitのGit内容で確認した。scoped diffと空白検査、新しい配置図・抽象モデル図と本文の対応も確認した。独立レビューで追加の修正必須事項はなかった。GitHub上の図の描画、人による引継ぎ演習、子リポジトリーの全面監査・履歴の公開審査は未実施。文書と参照だけの変更でファイル移動や実装変更がないため、実行系テストと依存の導入は行っていない。

リモート同期の試行は自動承認レビューにより実行前に拒否された。理由は、NDA関連情報を含む可能性がある11文書について、具体的な内容とGitHubへの送信先を対象とした明示承認が不足しているという判定である。同期先`flair-agency/live-agency`の`PRIVATE`設定、変更内容のレビュー、既存の開発同期方針は確認済みだが、この拒否を迂回しない。ローカル変更を保存し、同じ非公開リポジトリーの`codex/platform-knowledge-boundary`へのpushとPR作成、既存Issue #2・Projectへの記録を送信前の確認対象とする。PR・Issue・Projectはまだ更新しておらず、文書差分の準備完了とリモート同期待ちを区別する。

# 正本の採用済み方針と理由（参照）

| 整理 | 理由・保つ境界 |
| --- | --- |
| LIVEエージェンシー事業ドメインと、TikTokなど各LIVEプラットフォーム固有ドメインを区別する | Scouting／Managementは業務の区分、TikTokはプラットフォームの区分であり、片方で他方を置き換えない |
| ドメインモデルを含む知識の正本は`live-agency`の文書に集約する | 複数の実装が意味を別々に定義せず、人が根拠を読んで業務を引き継げるようにする |
| ユースケースごとにSkillが対応する | Skillが業務の進行・判断・計画・適用される承認・結果検証を持つ。Runtimeは選択済み環境へのアクセスを支える |
| 業務の論理スキーマ、Larkへの対応定義、実環境のIDを分ける | Lark Base ProviderにCreator Scouting／Creator Managementの業務定義を押し込めない |
| TikTokの共通知識、共通の取得処理、Web／iOS／BackStage固有の操作を区別する | 共通する意味を重複定義せず、画面や権限が異なる取得経路を同一視しない |
| ソース公開方針は`live-agency`・Skill・Runtime・Lark関連が公開、BackStageが非公開 | TikTok Web／iOSは非公開候補のまま。実際の公開変更、レジストリー配布、本番導入は別の作業・判断である |

知識を文書に集約しても、SkillやProviderが実装時にその知識を使わなくなるわけではない。正本を参照し、その意味を実装に反映する。認証画面の手順・未公開仕様・私有の証跡は、公開予定のドメイン文書へ転記せず、権限のある人が参照できるProvider側の知識として保持する。

招待可否は、Providerが返すステータスと招待区分を、Skillが内部の子ステータスへ対応させる整理を維持する。今回の文書化で新たなステータスや全件停止条件は追加しない。共通Creator UUIDや新しいマスターテーブルの導入、ScoutingとManagementの同一レコード化も行わない。

# 未決定の設計案

以下の図は2026-09-11の案を保持する。親への具象知識集約は今回の指示で失効している。新しい配置には上の図と移行順序を使い、旧図の公開境界を実装しない。

`SchemaBinding`は、論理スキーマの版、保存先の参照、フィールド・リンクの対応を宣言として表す候補である。業務判断や任意の実行コードを設定へ埋め込むものではない。既存の型検証・正規化・検索・添付・関連付けを、この定義と汎用操作だけで表せるかは確認が必要である。

独立したドメイン実装パッケージや、業務別の保存Provider／アダプターパッケージを必須にする案は採用していない。まずプロフィール1ユースケースで、必要な責務と既存処理との対応を確かめる。具体的なAPI名、再利用するマッピング定義の配置、文書の版と実装の版の結び方、TikTok Web／iOSの最終的な公開範囲は残る判断である。
